# Creating and revising skills

For a focused update, retain useful existing behavior and change only what the request needs. For a new skill, establish its purpose, narrow task triggers, scope, and any risk-specific constraints from available context. Reconsider inherited guidance that merely compensates for an older model; preserve real constraints that still protect users or data.

- Give `SKILL.md` frontmatter a `name` matching its directory and a short `description` stating what the skill does **and when to use it**. Avoid broad related-topic triggers that cause false activation or overlap with other skills. The description is loaded even when the skill is not selected, so earn every word.
- Keep the root skill lean. When it serves distinct workflows, make it a router to task-specific references or scripts; identify when to load each one. Put substantial on-demand knowledge in `references/`, useful deterministic work in `scripts/`, and material to copy into outputs in `assets/` only when it justifies maintenance. Link required resources directly from `SKILL.md`. Do not make every task read every reference.
- Describe decisions and guardrails in capability language that works across agent models. Avoid rigid itineraries, redundant generic advice, mandatory section layouts, and blanket read-or-test-everything rules. State authorization requirements for consequential actions the skill might enable, not for safe local edits or checks.
- Keep `agents/openai.yaml` consistent when the target uses it and the change affects its metadata. Check frontmatter, paths, links, and requested behavior. Use installed local validators such as `skillcheck <skill-dir>` or `agnix <skill-dir>` when relevant; do not install missing tools. For a meaningful behavioral change, exercise a representative task and, where uncertainty remains, a neighboring case. Match checks to the change rather than imposing a full suite or review ritual on a wording fix. Report what changed and what was actually checked.
